# Agentic-Bench — дизайн харнесса для оценки RAG-аугментаций

**Дата:** 2026-05-27
**Статус:** дизайн утверждён (блоки 1 и 2), ожидает финального ревью спеки

## 1. Цель и гипотеза

Построить харнесс, который прогоняет AI-агента **OpenCode** на фиксированной задаче в выбранном проекте и снимает полный агентский трейс (ReAct-цепочка: рассуждения, вызовы инструментов/команд, результаты, правки файлов), чтобы **сравнивать поведение агента между условиями**.

Основной исследовательский вопрос: помогают ли RAG-аугментации с графовыми срезами агентной разработке — а именно сокращают ли они ReAct-цепочки и число вызовов тестов, уменьшают ли объём «разведки» кода и время работы агента, без потери корректности результата.

Условия сравнения:
- **baseline** — агент получает только текст задачи;
- **augmented** — агент получает задачу + блок графового среза (RAG).

## 2. Ключевые решения

1. **Доставка аугментации = часть user-промпта.** System prompt фиксированный и одинаковый во всех условиях. Разница между baseline и augmented — только наличие блока среза в user-сообщении (как если бы пользователь сам вставил его в чат). Текст среза поставляет пользователь (строка/файл) на условие; харнесс его не генерирует.
2. **Корректность — ручная.** Харнесс сохраняет полный трейс и финальный дифф; вердикт «решено / не решено» выносит пользователь, сверяясь с эталоном. При этом процессные метрики (в т.ч. число вызовов тестов) всё равно извлекаются из трейса.
3. **Изоляция прогонов = копия фикстура + свежий git с одним коммитом.** На каждый прогон: копия подготовленного фикстура во временную папку → срез любого `.git` → `git init` + один коммит. Истории нет → оригинал методов не восстановить через VCS; git работает → чистый дифф штатно. Эталонные тела хранятся отдельно, вне досягаемости агента. На macOS APFS копия дёшева (`cp -c` / clonefile).
4. **Стек — Python.** Драйв OpenCode по HTTP API + поток событий; анализ/сравнение на pandas.
5. **Фикстур готовит пользователь.** Пользователь заранее вырезает тела методов и отдаёт харнессу готовую папку-фикстур + оригинал (эталон) отдельно. Харнесс не делает AST-операций → языконезависим. (Подготовка фикстура — ответственность пользователя, включая отсутствие утечки оригинала через комментарии/докстринги и `.orig`/бэкап-файлы.)
6. **Драйв OpenCode — подход A: сервер + живой поток событий.** Харнесс поднимает локальный `opencode serve`, создаёт сессию в cwd прогона, шлёт промпт, подписывается на поток событий и снимает каждый шаг вживую с таймингом; персистентная сессия — канонический бэкап трейса. Альтернатива B (`opencode run` + парсинг сессии постфактум) остаётся дешёвым откатом, т.к. A и B делят ~80% кода и различаются только адаптером.
7. **Модель — конфигурируемая, провайдер-агностичная.** `model` — строка в конфиге; ключ провайдера — из env. Подходят бесплатные варианты (OpenRouter `:free`, Google AI Studio Gemini Flash, Groq). Для валидности сравнения модель **запинена** на все условия и повторы (никаких тихих фолбэков).

## 3. Вне области (на старте; см. «Будущие расширения»)

- Автоматическая проверка корректности (автотесты/чекер/LLM-судья).
- Автоматическое вырезание тел методов (AST/tree-sitter).
- Docker-песочница.
- Параллельные прогоны.
- Матрица задач×проектов (suite); на старте — один эксперимент за запуск.
- Графики/дашборды (только таблицы CSV/markdown).

## 4. Архитектура и компоненты

Пакет `abench` (Python CLI). Принцип: один модуль — одна ответственность. Два шва изоляции:
- **адаптер** `opencode_client.py` прячет все специфики OpenCode;
- **нормализованный трейс** развязывает метрики/анализ от формата OpenCode.

| Модуль | Ответственность |
|---|---|
| `config.py` | Парсит и валидирует YAML эксперимента в типизированные объекты; проверяет существование путей и корректность условий. |
| `fixture.py` | На прогон: копия фикстура во временную папку (`cp -c`, иначе `copytree`) → срезает `.git` → `git init` + один коммит. Даёт `diff()` (git-патч против первого коммита) и cleanup. |
| `prompt.py` | Чистая функция `compose(task, augmentation) -> str` — собирает user-сообщение из задачи + (опц.) блока среза. |
| `opencode_client.py` | **Тонкий адаптер** — единственный, кто знает API OpenCode: старт/стоп `opencode serve`, фиксированный system prompt + модель через кастомного агента, создание сессии в cwd прогона, отправка сообщения, подписка на поток событий, чтение персистентной сессии. Здесь сосредоточены все «уточним при реализации» детали. |
| `trace.py` | Из событий (+ сессии) собирает нормализованный трейс: упорядоченный список типизированных шагов (`assistant_text` / `reasoning` / `tool_call{name,args}` / `tool_result{output,exit}` / `file_edit{path,patch}`) с таймстемпами и токенами. Пишет `events.jsonl` (сырьё) и `trace.json` (норма). |
| `metrics.py` | Чистая функция: нормализованный трейс + git-дифф → метрики. Пишет `metrics.json`. |
| `runner.py` | Оркестратор: для каждого условие×повтор гоняет цепочку fixture→prompt→adapter→trace→diff→metrics, пишет manifest, чистит копию. Последовательно по умолчанию (чистый тайминг). Изолирует сбои по прогонам. |
| `report.py` | Грузит все `metrics.json` в pandas, агрегирует по условиям (mean/median/std по повторам), пишет `summary.csv` + `summary.md` (baseline vs augmented с дельтами). |
| `cli.py` | `abench run experiment.yaml`, `abench report <dir>`. Тонкий. |

## 5. Конфиг эксперимента (YAML)

```yaml
name: refactor-exp-1
fixture_path: ./fixtures/proj-stripped     # подготовленный «изуродованный» проект
reference_path: ./fixtures/proj-original   # эталон, вне досягаемости агента (для ручной сверки)
task_prompt: ./prompts/task.md             # фиксированный текст задачи
system_prompt: ./prompts/system.md         # фиксированный system prompt, одинаковый везде
model: openrouter/<model-id>               # одинаковая (запиненная) модель во всех условиях
repetitions: 3
conditions:
  - {name: baseline,  augmentation: null}
  - {name: augmented, augmentation: ./slices/graph-slice.md}
output_dir: ./runs
opencode:
  port: 0                                   # 0 = авто-порт
  agent: bench                              # имя кастомного агента (детали в адаптере)
timeout_s: 600
min_seconds_between_runs: 0                 # пейсинг под RPM free-моделей
test_command_patterns:                      # для метрики n_test_runs (настраиваемо)
  - "pytest"
  - "(npm|pnpm|yarn) (run )?test"
  - "go test"
  - "cargo test"
  - "(jest|vitest)"
```

## 6. Раскладка артефактов

```
runs/<name>/
  experiment.resolved.yaml        # снимок резолвнутого конфига (воспроизводимость)
  <condition>/<rep_i>/
    manifest.json                 # условие, повтор, модель, промпты, тайминги, sha коммита
    events.jsonl                  # сырые события
    trace.json                    # нормализованный трейс
    changes.patch                 # финальный дифф агента
    metrics.json
  summary.csv
  summary.md
```

## 7. Поток одного прогона

1. `fixture.create()` → свежая копия + single-commit git → `workdir`.
2. `prompt.compose(task, augmentation)` → user-сообщение.
3. `opencode_client`: настроить агента (system prompt + модель), создать сессию в `workdir`, отправить сообщение.
4. Подписка на поток событий → `trace.record()` пишет `events.jsonl` вживую.
5. Завершение/таймаут → дочитать персистентную сессию → собрать `trace.json`.
6. `fixture.diff()` → `changes.patch`.
7. `metrics.extract(trace, diff)` → `metrics.json` + `manifest.json`.
8. Cleanup `workdir` (трейс/дифф остаются; тяжёлую копию удаляем, если без `--keep`).

По всем условие×повтор, затем `report.py` строит сводку.

## 8. Метрики (`metrics.py`)

Чистая функция над нормализованным трейсом + диффом → словарь метрик.

| Метрика | Что |
|---|---|
| `duration_s` | wall-clock от отправки до завершения |
| `n_steps` | число модельных шагов (assistant turns) — «длина ReAct-цепочки» |
| `n_tool_calls` | всего + разбивка по имени тула |
| `n_test_runs` | bash-вызовы, чья команда матчит `test_command_patterns` |
| `n_reads` / `n_searches` | read/grep/glob/list — прокси «объём разведки кода» |
| `n_files_edited`, `diff_lines_added`, `diff_lines_removed` | из git-диффа |
| `tokens_in` / `tokens_out` / `cost` | если поток/сессия отдают usage |
| `time_to_first_edit_s` | от старта до первой правки файла |
| `finished` | дошёл ли агент сам до конца |
| `interrupted_reason` | null \| timeout \| rate_limit \| error |
| `success` | null — заполняется вручную после сверки с эталоном |

## 9. Ошибки и детерминизм

- **Таймаут прогона** (конфиг) → `finished=false, interrupted_reason=timeout`; частичный трейс сохраняем; эксперимент продолжается.
- **Rate limit (429)** от free-модели → backoff с потолком; при исчерпании → `interrupted_reason=rate_limit`, прогон помечен невалидным (на диске остаётся, в агрегаты не идёт). Опц. `min_seconds_between_runs` — пейсинг под RPM.
- **Падение `opencode serve`** → адаптер перезапускает; неустранимо → прогон failed, остальные идут.
- Один плохой прогон **не роняет** весь эксперимент (runner изолирует сбои по прогонам).
- **Гард сравнимости:** модель запинена для всех условий/повторов; если на старте недоступна — падаем сразу, до прогонов.
- **Детерминизм:** temperature низкая/0 где поддерживается, но LLM стохастичны → отсюда повторы + агрегаты (mean/median/std). Free-модели могут игнорить temperature — документируем.
- **Анти-утечка:** отказ, если `.git` просочился в `workdir`; `reference_path` обязан быть вне `output_dir`/`workdir`.

## 10. Тестирование

- **Юнит (без opencode):** `prompt.compose`; `metrics.extract` на синтетических нормализованных трейсах (все счётчики, регэксп-детект тестов, `time_to_first_edit`, парсинг диффа); валидация `config` (good/bad YAML); `fixture` на крошечном temp-проекте (копия срезает `.git`, один коммит, дифф работает).
- **Нормализатор трейса:** golden-тест — один раз снимается реальный `events.jsonl` (после установки opencode) → проверяется нормализованная схема. Шов, которому нужен один живой образец.
- **Адаптер:** smoke-интеграция, скип если `opencode` не установлен — тривиальная задача на фикстуре из 1 файла end-to-end.
- **Репортер:** синтетические метрики по условиям → проверка сводной таблицы и дельт.

## 11. Открытые вопросы (уточнить на старте реализации)

Сети в текущей среде нет, `opencode` не установлен — поэтому следующие специфики OpenCode уточняются как **первый шаг реализации** (установить opencode, сверить по живому серверу/докам, подогнать только `opencode_client.py`):

- Точные REST-эндпоинты `opencode serve`: создание сессии с привязкой к cwd, отправка сообщения, выбор модели.
- Механизм фиксированного system prompt (кастомный агент: `opencode.json` / agent-файл; поля `prompt`/instructions; автозагрузка `AGENTS.md`) и как сделать его идентичным во всех прогонах.
- Эндпоинт и схема потока событий (типы событий: части сообщения, tool-call start/finish, step start/finish, usage).
- Путь и схема персистентного хранилища сессий (для канонического трейса постфактум).
- Конфигурация провайдера/ключа для batch-режима (OpenRouter/Google/Groq), актуальные ID и квоты бесплатных моделей.
- Поддержка параллелизма (порт/конкурентные сессии) — на будущее.
